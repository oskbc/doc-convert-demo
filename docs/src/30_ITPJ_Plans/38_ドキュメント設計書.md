## 1. 本書の目的
本プロジェクトで作成するドキュメントの構成、記述ルール、および各担当者の責任範囲（分掌）を定義し、ドキュメント品質の均一化と保守性の向上を図る。

## 2. ドキュメント体系と格納ルール
### 2.1. ディレクトリ構造
本プロジェクトのドキュメントは以下のディレクトリ構成で管理する。

```text
docs/src/
　├── 00_General/        # 議事録、日報、調査報告書
　├── 10_Sales/          # 見積、契約、提案資料
　├── 20_ITPJ_Specs/     # システム仕様詳細（個別カタログ）
　├── 30_ITPJ_Plans/     # 計画書、要件定義、管理台帳
　├── 40_Design_Detail/  # 詳細設計書（集約版）
　├── 50_Test/           # テスト計画・設計・結果
　├── 60_Migration/      # 移行・リリース計画・手順
　├── 70_Operation/      # 運用保守マニュアル
　└── 99_Guide/          # 執筆ガイドライン
```

### 2.2. ドキュメント間の参照関係

情報の重複を防ぐため、詳細な仕様値については「20\_ITPJ\_Specs」配下のファイルをマスタとし、他の計画書や設計書からはリンク参照を行う。

  - **基本設計書/詳細設計書**: 全体方針のみを記述し、各機能の詳細は `20_ITPJ_Specs` を参照する。
  - **参照記述例**:
      - `詳細は [画面一覧](../20_ITPJ_Specs/24_画面一覧.md) を参照のこと。`

## 3\. 記述・フォーマットルール

### 3.1. ファイル命名規則

  - `No_ドキュメント名.md` とする。
  - Noは「ドキュメント計画書」の管理番号と一致させる。
  - 例: `24_画面一覧.md`, `37_ドキュメント計画書.md`

### 3.2. 記述スタイル

  - **言語**: 日本語（常体・である調）を基本とする。
  - **図表**: Mermaid記法を推奨するが、表現力が不足する場合は画像添付（`.png`）を許容する。
  - **強調**: 重要な項目は `**太字**` で強調する。

## 4\. 責任分掌（RACIチャート）

各ドキュメントカテゴリにおける役割分担は以下の通りとする。

| カテゴリ | 作成 (R) | 説明責任/承認 (A) | 相談/レビュー (C) | 報告 (I) |
| :--- | :--- | :--- | :--- | :--- |
| **00\_General** | 各担当者 | PM | - | 全体 |
| **10\_Sales** | 営業担当 | 営業MGR | PM, 技術担当 | - |
| **20\_ITPJ\_Specs** | SE/PG | リードSE | PM, 顧客担当 | - |
| **30\_ITPJ\_Plans** | PM/PL | 顧客責任者 | ステークホルダー | 開発チーム |
| **50\_Test** | QA/テスター | PM/品質MGR | 開発チーム | - |

  - **R (Responsible)**: 実行責任者。ドキュメントを作成する。
  - **A (Accountable)**: 説明責任者。最終承認を行う。
  - **C (Consulted)**: 協業先。作成にあたり情報提供やレビューを行う。
  - **I (Informed)**: 報告先。決定事項の共有を受ける。

## 5\. レビュー・更新フロー

1.  **ドラフト作成**: 作成担当者はfeatureブランチにて作成し、Pull Requestを作成する。
2.  **レビュー**: レビュー担当者（C/A）はPR上でコメントを行う。
3.  **承認・マージ**: 承認者（A）がApprovedとし、mainブランチへマージする。
4.  **版数管理**: タグ付けまたはリリースノートにより版数を管理する。
