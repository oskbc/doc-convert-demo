## 1. 本書の目的・分掌
本ドキュメントは、テスト計画書に基づき、テストを実施するために必要な**テスト環境、データ、およびテストケース作成の方針（観点）**を具体化することを目的とする。

- **テスト計画書 (No.45)**: 戦略、スケジュール、体制を定義（Strategy）。
- **テスト設計書 (本書)**: 環境構築要件、データ要件、テスト観点を定義（Design）。
- **テストシナリオ (No.47)**: 具体的な確認手順、期待値、合否判定基準を定義（Case）。

## 2. テストの種類と実行方法
各フェーズにおける具体的なアプローチを定義する。

| 工程 | テスト対象 | 実行方法・ツール | 判定基準 |
| :--- | :--- | :--- | :--- |
| **UT** | クラス/メソッド | xUnitによる自動テスト<br>一部手動デバッグ実行 | C1カバレッジ 80% |
| **IT** | 機能間連携<br>API | Postman/Swagger UI<br>ブラウザ手動操作 | 疎通確認OK<br>データ整合性OK |
| **ST** | 業務シナリオ | ブラウザ手動操作<br>実機検証 | シナリオ完遂 |
| **非機能**| 性能・負荷 | JMeter / Gatling | 目標RPS達成 |

## 3. テスト環境設計
### 3.1. システム構成
テスト実施環境のインフラ・ミドルウェア構成。
基本構成は **[18_システム構成図](../20_ITPJ_Specs/18_システム構成図.md)** に準拠するが、テスト固有の相違点を以下に定める。

| 構成要素 | 本番環境 | 検証(ST)環境 | 開発(UT/IT)環境 | 備考 |
| :--- | :--- | :--- | :--- | :--- |
| **Web/AP** | 冗長構成 (Multi-AZ) | シングル構成 | ローカルDocker | コスト削減のため |
| **DB** | AWS RDS (本番) | AWS RDS (小規模) | ローカルコンテナ | データ量は本番の10%程度 |
| **外部連携** | 決済代行 本番環境 | 決済代行 **サンドボックス** | 決済代行 **Mock/Stub** | |
| **メール** | 実際のメール送信 | MailTrap等へ送信 | コンソール出力 | 誤送信防止 |

### 3.2. テストデータ設計
各テストフェーズで利用するデータの準備方針。

- **マスタデータ**:
    - 本番相当の完全なマスタセットを用意する（商品、拠点、税率など）。
    - 準備担当: アプリケーションチーム
- **トランザクションデータ**:
    - **初期状態**: ユーザ登録直後の「データなし」状態。
    - **進行状態**: 業務フロー途中（受注済み・未出荷など）のデータをSQLで投入。
- **個人情報マスキング**:
    - 本番データのコピーを利用する場合は、氏名・電話番号・メアドを匿名化スクリプトで変換後に環境へロードする。

## 4. テスト環境ライフサイクル
テスト環境の構築から廃棄までのスケジュール。

1.  **構築**: ST開始の2週間前までにインフラチームが構築。
2.  **データ投入**: 各テストサイクルの開始前にDB初期化スクリプトを実行。
3.  **フリーズ**: リリース判定会議の3日前からは設定変更を凍結。
4.  **リフレッシュ**: 次期開発フェーズ開始時に最新の本番データ（マスク済）で更新。

## 5. 単体テスト（UT）設計
### 5.1. 目的・分掌
- **目的**: ロジック単位でのバグ排除。
- **担当**: 開発担当者自身が実装と並行して実施。

### 5.2. テスト観点（リスト）
- **正常系**: 標準的な入力値で期待通りの戻り値・DB更新が行われるか。
- **異常系**: 必須欠け、型違反、最大長超過、存在しないID指定時のエラーハンドリング。
- **境界値**: 閾値（0, 1, 99, 100等）での挙動。

## 8. 受入テスト（UAT）設計案
顧客（ユーザ）が主体となって行うテストの支援設計。

- **推奨確認期間**: 2週間
- **推奨シナリオ**: 実際の業務で「よくあるケース」と「稀だが重要なケース」をピックアップ。
- **データ**: 顧客側で用意した「本番想定データ」のCSV取り込みテストを含む。

## 9. 非機能・運用テスト設計
### 9.1. 性能テスト
- **対象**: 検索API、注文確定API
- **条件**: 同時アクセス 50スレッド、ランプアップ期間 60秒
- **合格基準**: エラー率 0%、平均レスポンス 2秒未満

### 9.2. セキュリティテスト
- **対象**: 外部公開URL全般
- **手法**: 脆弱性診断ツールによるスキャン、および権限昇格攻撃の手動試行。

### 9.3. 運用テスト
- **障害試験**: DBフェイルオーバー時のWebサーバ再接続確認。
- **バックアップ試験**: 取得したバックアップからのリストア所要時間計測。
- 手順は **[54_運用・保守手順書](../70_Operation/54_運用・保守手順書.md)** の検証を兼ねる。

## 10. 課題と対応
- テストデータの準備において、個人情報のマスキングツールの選定が未完了。早急に選定する。
- 決済代行会社のサンドボックス環境がメンテナンスで使用できない期間があるため、スケジュール調整が必要。
