## 1. 本書の目的・分掌
本ドキュメントは、**[53_運用・保守計画書](./53_運用・保守計画書.md)** に基づき、システムの定常運用および障害発生時の具体的な**作業手順（コマンド、操作方法）**を定義する。

- **対象読者**: システム運用担当者、ヘルプデスク、保守開発エンジニア
- **利用シーン**: 日々の定型作業、アラート検知時の初動対応、月次報告作成時

## 2. インシデントレベル基準
事象が発生した際、どの程度の緊急度で対応すべきかを判断する基準。

| レベル | 呼称 | 定義・影響範囲 | 対応目標 | 連絡対象 |
| :---: | :--- | :--- | :--- | :--- |
| **Lv.1** | **情報/軽微** | システム利用に影響なし。<br>（例：単発の警告ログ、ユーザからの操作質問） | 翌営業日中 | 運用チーム内 |
| **Lv.2** | **警告** | 一部機能または特定ユーザのみ影響あり。回避策あり。<br>（例：特定帳票が出力できない、軽微なバグ） | 4時間以内 | + PL/PM |
| **Lv.3** | **重度** | 業務遂行が困難だが、全面停止ではない。<br>（例：システムレスポンスの大幅低下、主要機能のエラー） | **即時着手**<br>（2時間以内復旧） | + 顧客担当者 |
| **Lv.4** | **緊急** | サービス全面停止、またはデータ消失・漏洩。<br>（例：ログイン不可、DB接続エラー） | **緊急招集**<br>（最優先） | + 経営層<br>+ 全利用者 |

## 3. 連絡・エスカレーションフロー
障害検知から解決までの連絡経路。

```mermaid
flowchart TD
    Detect[検知 (アラート/問合せ)] --> Check{一次切り分け}
    
    Check -->|手順書で対応可| Manual[手順書対応 (Lv.1-2)]
    Check -->|手順書なし/Lv.3以上| Esc[エスカレーション]
    
    Manual --> Report[対応記録・完了]
    
    Esc --> PL[プロジェクトリーダー]
    PL --> Dev[開発担当 (調査)]
    PL --> Client[顧客連絡 (第一報)]
    
    Dev --> Fix[修正・復旧作業]
    Fix --> Client[復旧連絡]
    Fix --> ReportAccident[事故報告書作成]
```

  - **緊急連絡先リスト**: 別紙「緊急連絡網.xlsx」を参照のこと。
  - **チャット通知**: Slackチャンネル `#ops-alert` にて第一報を行う。

## 5\. 各手順詳細

### OP-01: 日次ログ確認・バックアップ確認

  - **前提**: 監視ツール（Datadog/CloudWatch）へのアクセス権限があること。

**【手順】**

1.  監視ダッシュボード「Daily Check」を開く。
2.  過去24時間の `ERROR` レベルのログ件数が「0件」であることを確認する。
      - 0件でない場合は、内容を確認しチケット起票する。
3.  RDSのスナップショット一覧を開き、今朝（AM 3:00）のバックアップが `available` であることを確認する。

**【異常時の対応】**

  - バックアップが失敗している場合、手動でスナップショット取得を実行し、失敗原因（容量不足等）を調査する。

-----

### OP-02: アカウント発行・削除

  - **前提**: 管理者権限（Admin）でログインできること。
  - **入力**: 「アカウント申請書」を受領していること。

**【手順】**

1.  管理画面 \> ユーザ管理 \> 新規登録 を開く。
2.  申請書の通りに `氏名`, `Email`, `権限ロール` を入力する。
3.  初期パスワードを自動生成し、設定する。
4.  登録ボタンを押下する。
5.  申請者へ、メール以外の手段（チャット等）で初期パスワードを通知する。

**【FAQ】**

  - Q. 招待メールが届かないと言われた。
  - A. 迷惑メールフォルダを確認依頼してください。それでも届かない場合は、登録メアドが正しいか再確認してください。

-----

### TR-01: サービス再起動手順

  - **対象**: Web/APサーバ (ECS/EC2)
  - **発動条件**: Lv.3以上のアラート（応答なし）が発生し、PLの承認が得られた場合。

**【手順】**

1.  踏み台サーバへSSH接続する。
2.  以下のコマンドでサービスのステータスを確認する。
    ```bash
    systemctl status web-service
    ```
3.  サービスを再起動する。
    ```bash
    sudo systemctl restart web-service
    ```
4.  起動ログを監視し、エラーが出ないことを確認する。
    ```bash
    journalctl -u web-service -f
    ```
5.  ブラウザでアクセスし、復旧を確認する。

**【エラー・想定外事項】**

  - 再起動しても `Failed` となる場合は、直前のデプロイ起因の可能性があるため、手順 `TR-05: 切り戻し手順` へ移行する。

### 6.1. 月次運用報告書テンプレート

毎月初第3営業日までに提出する定例報告用。

```markdown
# 202X年XX月度 運用報告書

## 1. 稼働状況サマリ
- **システム稼働率**: 99.9% (停止時間: 30分)
- **利用者数**: Max 120ユーザ / Avg 80ユーザ
- **リソース状況**: 
    - CPU: Avg 20% / Max 60%
    - Disk: 使用率 45% (残り 500GB)

## 2. 障害・インシデント発生状況
| 発生日 | レベル | 件名 | ステータス |
| :--- | :--- | :--- | :--- |
| MM/DD | Lv.2 | 〇〇帳票の印字ズレ | 対応完了 |
| MM/DD | Lv.1 | パスワード忘れ問合せ増 | 完了 |

## 3. 実施した主な作業
- 定期メンテナンス（OSパッチ適用）: MM/DD 実施
- アカウント棚卸し: 異常なし

## 4. 課題・申し送り事項
- ディスク容量が前月比+5%で増加中。3ヶ月後に拡張を検討する必要あり。
```

### 6.2. 事故報告書（障害報告書）テンプレート

Lv.3以上の障害発生時に、顧客へ提出する謝罪・原因報告用。

```markdown
# 事故報告書（障害経緯報告書）
提出日: 202X年XX月XX日

## 1. 障害概要
- **発生日時**: 202X/MM/DD 14:00 〜 15:30 (1時間30分)
- **影響範囲**: 全ユーザがシステムにログイン不可
- **事象**: ログイン画面にて「システムエラー（500）」が表示される。

## 2. 原因
- **直接原因**: DBのコネクション数が上限（Max Connection）に達し、新規接続が拒否されたため。
- **根本原因**: ランペーンのお知らせ配信により、想定の3倍のアクセスが一時的に集中したが、コネクションプールの設定値が通常時のままであったため。

## 3. 対応時系列（タイムライン）
| 時刻 | 内容 | 対応者 |
| :--- | :--- | :--- |
| 14:00 | 監視アラート検知（HTTP 500 Error） | 自動 |
| 14:05 | 運用担当者が調査開始。DB接続エラーを確認。 | 佐藤 |
| 14:15 | 再起動では復旧しないと判断。設定値変更を検討。 | 鈴木 |
| 14:30 | 顧客へ第一報（状況報告）。 | 田中 |
| 14:50 | DBパラメータ変更適用（MaxConn: 100 -> 500）。 | 鈴木 |
| 15:00 | サービス再起動。順次ログイン可能を確認。 | 佐藤 |
| 15:30 | 負荷が安定していることを確認し、完全復旧宣言。 | 田中 |

## 4. 再発防止策
| No | 対策内容 | 実施予定日 |
| :--- | :--- | :--- |
| 1 | **暫定** | DBスペックの見直しとオートスケーリング設定の検討。 | 即時 |
| 2 | **恒久** | コネクションプーリング機能（PgBouncer等）の導入。 | 次回メンテ |
| 3 | **運用** | 大規模配信前の事前連絡ルールの徹底。 | 即時 |
```
