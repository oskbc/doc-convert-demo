# 59. 見た目

## 1. 本規定の目的
ドキュメントの「見た目」がバラバラだと、読み手は内容の理解よりも「読み解くこと」に脳のリソースを使ってしまいます。
**「誰が書いても同じように見える」**状態を目指し、以下のルールを遵守してください。

## 2. フォント・文字設定
### 2.1. フォントファミリ（Office/PDF）
特別な意図がない限り、以下の標準フォントを使用すること。

| 種別 | Windows | Mac | 備考 |
| :--- | :--- | :--- | :--- |
| **日本語** | **メイリオ** または **游ゴシック** | **ヒラギノ角ゴ** | MS明朝などのセリフ体は、長文の印刷物以外では避ける（画面で見づらいため）。 |
| **英数字** | **Segoe UI** または **Arial** | **Helvetica** | 日本語フォントの英数（全角）は使わず、半角英数を使用する。 |
| **コード** | **Consolas** | **Monaco** | 等幅フォントを使用する。 |

### 2.2. 文字サイズと階層
視覚的な階層構造（ジャンプ率）を意識する。

- **タイトル (H1)**: 24pt 〜 32pt / 太字
- **大見出し (H2)**: 18pt 〜 24pt / 太字 / 下線など装飾あり
- **中見出し (H3)**: 14pt 〜 16pt / 太字
- **本文 (Body)**: **10.5pt 〜 12pt**
- **注釈**: 9pt 〜 10pt / 灰色など

### 2.3. 強調表現
- **太字**: 重要なキーワードのみに使用する。文全体を太字にしない。
- **赤字**: 「危険」「禁止」「重大な注意」のみに使用する。単なる強調で赤を使わない。
- **色数**: 原則として**3色以内**（黒・アクセントカラー・注意色）に抑える。

## 3. Markdown記法の統一ルール
Github等でのプレビュー結果を統一するため、以下の記法を守ること。

### 3.1. 見出し（Headers）
`#` の数で階層を表現する。
- 悪い例: 本文中の強調のために `###` を使う。
- 良い例: 文書構造として `##` の次は `###` を使う。

### 3.2. 空行とスペース
- **段落間**: 必ず1行空ける。
- **リストの前後**: 必ず1行空ける（レンダリング崩れ防止）。
- **英数と日本語の間**: 半角スペースを入れると読みやすい（任意だが推奨）。
    - 例: `Gitの使い方は...` → `Git の使い方は...`

### 3.3. コードブロック
コードやファイルパス、コマンドは必ずバッククォートで囲む。
- インライン: `` `setting.json` ``
- ブロック:
```bash
  npm install
```

## 4\. 図表のルール

  - **アスペクト比**: 図を引き伸ばして縦横比を崩さない。
  - **解像度**: スクリーンショットは文字が読める解像度を保つ。
  - **キャプション**: 図表の下（または上）に必ず「図1. システム構成図」のような名称を付ける。

## 5\. チェックリスト（提出前確認）

ドキュメントを公開・提出する前に、以下を確認すること。

  - [ ] **表記揺れ**はないか？（例：ユーザ / ユーザー / User）
  - [ ] **誤字脱字**はないか？
  - [ ] **「だ・である」調** と **「です・ます」調** が混在していないか？（基本は「だ・である」推奨）
